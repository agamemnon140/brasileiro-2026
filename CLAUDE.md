# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-page React app that simulates the 2026 Brazilian Brasileirão (Séries A, B, C, D + Copa do Brasil) using an Elo + Poisson goal model run through Monte Carlo. It is a PWA (installable, offline-capable) shipped as **one standalone HTML file** with React/ReactDOM/Tailwind pulled from CDNs. UI text is in Brazilian Portuguese.

## Repo

The working repo is named `brasileirao-2026` (same name as the app and its built HTML); this directory is the project root. It is published to GitHub as `agamemnon140/brasileiro-2026` (note the spelling difference) and served by GitHub Pages at <https://agamemnon140.github.io/brasileiro-2026/>.

## Critical: git is the source of truth — sync before doing anything

**Always work from the files as they exist in git, and start every session by syncing.** The GitHub Action commits to `main` on its own (see *Automatic result updates*), so a local checkout goes stale on its own schedule, with no action from anyone. A stale checkout has repeatedly caused false conclusions — reading a `CLAUDE.md` that describes a retired pipeline, or opening a months-old `index.html` next to an empty `results.json` and concluding the automation was broken when it was working fine.

```bash
git fetch origin && git status -sb   # check drift BEFORE reading or editing anything
git pull --ff-only                   # then bring the checkout up to date
```

Before answering any question about the app's live behavior or the automation's output, check what is actually on `origin/main` (`git show origin/main:<file>`, `gh api`, or the Pages URL) rather than trusting the working copy. If the working tree disagrees with `origin/main`, `origin/main` wins — reconcile first, then work. Uncommitted local files whose names do not match anything on `origin/main` are usually superseded leftovers from a rename, not work in progress; check the history before treating them as current.

This applies to `CLAUDE.md` itself: if this file contradicts the code, verify against the code on `origin/main` and fix the file.

## Source layout — read this before editing app logic

**`index.html` is the source.** There is no build step and no `.jsx` any more.

- `index.html` / `brasileirao-2026.html` — kept byte-identical; `index.html` is what Pages
  serves. This transpiled HTML is the source of truth: it is at **v4.64** and every change
  since v4.48 was made by hand, directly in `React.createElement` form.
- `results.json` — automation output, **written by the Action, not by hand** (see *Automatic
  result updates*). Never hand-edit the `results`/`ko_d`/`cb` arrays and never commit an
  emptied one: it gets clobbered by the next run and masks real results meanwhile. Envelope
  *metadata* is the one exception — backfilling a newly added field is fine, since the next
  run overwrites it with computed values. Match data, never; metadata with a verified source,
  acceptable.
- `icon_b64.json`, `icon-512.png` — PWA icon assets (generated by an external `make_icon.py`).
- `scripts/engine.cjs` — extracts the pure engine (simulation + data) out of `index.html` so
  headless harnesses can `require` it. See *Verifying changes*.

So: **apply logic changes directly to `index.html`, then copy it over `brasileirao-2026.html`**
so the two stay identical (verify with `md5sum`). Editing transpiled `React.createElement` by
hand is unpleasant but is the only path. Prefer a scripted, assertion-checked patch (count
occurrences, fail on anything but the expected number) over hand-editing a 790 KB file — a
stray match in the Config-tab copy of the same expression is an easy mistake. Known duplicate
anchors: `tab === 'config'` (2), `grupoTop1: 0` (2), `extraStats.__uf = {` (2).

> **Removed:** `simulador_unificado.jsx` and `build_html.js` were deleted once the last
> consumers (the two harnesses) stopped reading them. The `.jsx` had been abandoned at v4.47
> on 2026-06-08 while the HTML moved on to v4.64, so running `build_html.js` would have
> silently regressed seventeen versions — it contained none of the Série D knockout, the
> `results.json` loading, or the Copa do Brasil automation. Git history keeps both if the
> transpiled-source decision is ever revisited.

## Verifying changes

There is no test suite or linter. Two mechanisms:

- **Headless harnesses** (`scripts/*.cjs`). `engine.cjs` slices `index.html` from the changelog
  down to the `ReactDOM.createRoot` bootstrap and evaluates it, exposing every engine symbol.
  The cut must reach the bootstrap, not stop at the first UI symbol: `SD_C_CODES` /
  `SD_D_CODES` / `SD_BRK_PAIRS` are declared after the components but used by
  `simMC_D_single`. Boundaries are textual markers, never line numbers — a `slice(0, 1146)`
  rots silently, which is exactly what happened to the previous harnesses.
  `node scripts/validate_ufdist.cjs` should print `RESULT: PASS`.
- **Screenshots** — `.claude/skills/verify/` documents a headless-Edge recipe. Stubbing
  `window.fetch` in a scratchpad copy of the HTML is the way to exercise
  `results.json`-dependent UI without a live file.

To run the app, prefer the deployed Pages URL. Opening the local HTML works too, but note it
fetches `results.json` by **relative path** — so a stale or empty local `results.json` silently
yields an app with no automated results, and over `file://` the fetch may be blocked outright.
Never diagnose the automation from a locally-opened file; check the Pages URL or `origin/main`.

## Architecture of the app

Top-level component `SimuladorUnificado` holds a `tab` state switching between: `serieA`/`serieB`/`serieC` (→ `LeagueSim`), `serieD` (→ `SerieDSim`), `copaBR` (→ `CopaBrasilSim`), `h2h` (→ `ConfrontoMerged`), `config` (→ `SettingsTab`). A "Simular Tudo" dashboard is the **single Monte Carlo channel** — individual tabs only keep a "1 Sim rápido" button.

**Simulation engine** (pure functions, no React): `poissonProb` → `calcProbs`/`calcL` (Poisson goal expectations from Elo + atk/def), `updR` (Elo + atk/def update after a game), `applyDrift`/`boxMuller` (per-sim structural-uncertainty noise on Elo and atk/def), `initLeague`/`computeCurrentAD`/`backtestSeries` (derive current team strength from real results played so far), `simMC` (N-run Monte Carlo, 1k or 10k) and `simUnica` (single deterministic-ish run). Each series has special post-season logic: Série B access playoff (3º–6º), Série C final quadrangular (G8 → 2 groups → final ida/volta), Série D's large multi-phase knockout handled via `prepareSerieDState` + `pairKey` (matches results to fixtures by sorted-pair+leg, not exact home/away/round).

**Per-series data** is hardcoded as `S{A,B,C}_TAB` (fixtures), `_RES` (real results played), `_RANKING`, `_DATES`, `_NM`, plus `_META` objects (e.g. `nReb` relegation count, zone cutoffs — these encode 2026 CBF format changes like Série C having only 2 relegated). Copa do Brasil uses `CB_RES_IDA`/`CB_RES_VOLTA`. Results are merged with user-fetched results from `localStorage`.

**`UpdaterPanel`** ingests new real results: it downloads a CBF PDF through the `allorigins.win` CORS proxy, then calls the Anthropic Messages API (`api.anthropic.com/v1/messages`, model `claude-sonnet-4-6`) with the PDF as a document block to extract finished matches as a JSON array, which is merged and persisted. API key resolution order: `window.__ANTHROPIC_API_KEY__` (build-time placeholder `__ANTHROPIC_API_KEY__`, optionally replaced by a CI secret) → `localStorage['simUni_apiKey']` → manual entry. There is a fully manual fallback ("Copiar prompt" + paste JSON) when no key/proxy is available.

**localStorage keys**: `simUni_apiKey`, `simUni_fetchedRes`.

**Automatic result updates** (added separately from the app source): a twice-weekly GitHub Action (`.github/workflows/update-tables.yml`, cron `0 9 * * 1,5` — Monday and Friday 09:00 UTC — plus manual dispatch) on the repo `agamemnon140/brasileiro-2026` runs `scripts/fetch_tables.mjs`: it discovers the current official CBF "Tabela Detalhada" PDFs via the public Strapi CMS (`cms.cbf.com.br/api/championship-documents`, type "Complemento de Tabela" — the blob URL hash changes weekly), downloads them (cms.cbf.com.br serves an incomplete TLS chain, hence `NODE_EXTRA_CA_CERTS` pointing at the vendored `scripts/cbf-ca.pem`), extracts played league-phase results with the Anthropic API (PDF document block) and merges them into `results.json` at the repo root, committing on change so GitHub Pages redeploys. Since v4.59 it also covers the **Série D knockout**: the D PDF's mata-mata legs (GR code + ida/volta + penalties) go into the `ko_d` field of `results.json`, which the app converts into `SD_KO_AUTO`/`SD_KO_PART_AUTO` overlays (precedence: user edits > hardcoded > automation) feeding the MC, the bracket defaults, the Geral tab and the Config log. Copa do Brasil knockout still ships via versioned app updates. It skips games already hardcoded in the app by parsing `SA/SB/SC_RES` (and `SD_F2_REAL`/`SD_F3_REAL` for D — keep those parses updated when consolidating new knockout phases) out of `index.html`. The app loads `results.json` on mount via a `useEffect` (injected just after `handleSearchResults` in `SimuladorUnificado`, in both `index.html` and `brasileirao-2026.html`), feeds it through the same `handleSearchResults` pipeline, and the dashboard auto-run waits for that fetch to settle (v4.55c). Server-side guardrails: canonical-team allowlist + `NORM_NAME` map (kept in sync by hand with the app team lists), score range 0–14, round 1–38, never overwrites a recorded score (logs conflicts), per-run volume cap. An earlier web-search-based Action (`fetch_results.mjs` + `update-results.yml`, Anthropic `web_search` tool) was retired in favor of the official PDFs — see git history if it's ever needed again. The Action needs the repo secret `ANTHROPIC_API_KEY`; the API key is never exposed client-side here.

**Reading the automation's output correctly.** The envelope carries a `last_run` block (`{at, added, ko_added, total_new}`) recording what **that run** contributed. The badge under the app title shows that delta — `📡 Tabelas CBF atualizadas em <data> · +N novo(s) nesta atualização` — and keeps the cumulative total in its `title` tooltip; the Config tab still lists the cumulative figure, labelled "acumulados". Envelopes written before `last_run` existed fall back to the old cumulative wording, so both shapes render.

Because the writer returns early when nothing changed, `results.json` is only rewritten on a real change: `updated_at`/`last_run` always describe the last **effective** update, and a no-op run leaves the badge showing the previous one. That is intended — but it means the badge alone cannot tell you whether this week's run executed. Check the Action for that. A run legitimately adds nothing when the CBF has not republished that série's PDF (the discovered blob URL is unchanged from the previous week), so "no new results" is an expected mid-week outcome and is not evidence of a broken key or exhausted credits. Real API failures surface as a failed step in the Action, not as a silent empty diff; `gh run view <id> --log` and its `Resumo: +X liga + Y mata-mata D novos, ...` line are the ground truth for any given run.

## Conventions

- The big comment block at the top of `index.html` is a **running changelog** (v4.x). When making a substantive change, add a dated/versioned entry there describing the fix and its rationale — this is the project's primary record of why things are the way they are.
- Series-format rules (relegation counts, access slots, playoff/quadrangular structures) reflect specific **2026 CBF regulations** and have been corrected repeatedly; verify against the regulation before changing zone cutoffs or `nReb`.
- Watch for call-stack overflow: the code uses a `minMax()` loop instead of `Math.min/max(...arr)` because Série D produces very large sample arrays (~960k).
