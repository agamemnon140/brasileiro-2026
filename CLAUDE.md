# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-page React app that simulates the 2026 Brazilian Brasileirão (Séries A, B, C, D + Copa do Brasil) using an Elo + Poisson goal model run through Monte Carlo. It is a PWA (installable, offline-capable) shipped as **one standalone HTML file** with React/ReactDOM/Tailwind pulled from CDNs. UI text is in Brazilian Portuguese.

## Repo

The working repo is named `brasileirao-2026` (same name as the app and its built HTML); this directory is the project root. It is published to GitHub as `agamemnon140/brasileiro-2026` (note the spelling difference) and served by GitHub Pages at <https://agamemnon140.github.io/brasileiro-2026/>.

## Critical: git is the source of truth — sync before doing anything

**Always work from the files as they exist in git, and start every session by syncing.** The GitHub Action commits to `main` on its own (see *Automatic result updates*), so a local checkout goes stale on its own schedule, with no action from anyone. A stale checkout has repeatedly caused false conclusions — reading a `CLAUDE.md` that describes a retired pipeline, or opening a months-old `index.html` next to an empty `results.json` and concluding the automation was broken when it was working fine.

```bash
git fetch origin && git status -sb   # check drift BEFORE reading or editing anything
git pull --ff-only                   # then bring the checkout up to date
```

Before answering any question about the app's live behavior or the automation's output, check what is actually on `origin/main` (`git show origin/main:<file>`, `gh api`, or the Pages URL) rather than trusting the working copy. If the working tree disagrees with `origin/main`, `origin/main` wins — reconcile first, then work. Uncommitted local files whose names do not match anything on `origin/main` are usually superseded leftovers from a rename, not work in progress; check the history before treating them as current.

This applies to `CLAUDE.md` itself: if this file contradicts the code, verify against the code on `origin/main` and fix the file.

## Source layout — read this before editing app logic

**`index.html` is the source.** There is no build step and no `.jsx` any more.

- `index.html` / `brasileirao-2026.html` — kept byte-identical; `index.html` is what Pages
  serves. This transpiled HTML is the source of truth: it is at **v4.98** and every change
  since v4.48 was made by hand, directly in `React.createElement` form.
- `results.json` — automation output, **written by the Action, not by hand** (see *Automatic
  result updates*). Never hand-edit the `results`/`ko_d`/`cb`/`quad_c` arrays and never commit an
  emptied one: it gets clobbered by the next run and masks real results meanwhile. Envelope
  *metadata* is the one exception — backfilling a newly added field is fine, since the next
  run overwrites it with computed values. Match data, never; metadata with a verified source,
  acceptable.
- `icon_b64.json`, `icon-512.png` — PWA icon assets (generated by an external `make_icon.py`).
- `scripts/engine.cjs` — extracts the pure engine (simulation + data) out of `index.html` so
  headless harnesses can `require` it. See *Verifying changes*.

So: **apply logic changes directly to `index.html`, then copy it over `brasileirao-2026.html`**
so the two stay identical (verify with `md5sum`). Editing transpiled `React.createElement` by
hand is unpleasant but is the only path. Prefer a scripted, assertion-checked patch (count
occurrences, fail on anything but the expected number) over hand-editing a 790 KB file — a
stray match in the Config-tab copy of the same expression is an easy mistake. Known duplicate
anchors: `tab === 'config'` (2), `grupoTop1: 0` (2), `extraStats.__uf = {` (2).

> **Removed:** `simulador_unificado.jsx` and `build_html.js` were deleted once the last
> consumers (the two harnesses) stopped reading them. The `.jsx` had been abandoned at v4.47
> on 2026-06-08 while the HTML moved on to v4.64, so running `build_html.js` would have
> silently regressed seventeen versions — it contained none of the Série D knockout, the
> `results.json` loading, or the Copa do Brasil automation. Git history keeps both if the
> transpiled-source decision is ever revisited.

## Architecture of the app

Top-level component `SimuladorUnificado` holds a `tab` state switching between: `serieA`/`serieB`/`serieC` (→ `LeagueSim`), `serieD` (→ `SerieDSim`), `copaBR` (→ `CopaBrasilSim`), `rnc` (→ `RankingNacionalSim`), `uf27` (→ `Estados2027Sim`), `evolucao` (→ `EvolucaoSim`), `h2h` (→ `ConfrontoMerged`), `config` (→ `SettingsTab`). A "Simular Tudo" dashboard is the **single Monte Carlo channel** — individual tabs only keep a "1 Sim rápido" button. Since v4.84 the dashboard card of a série whose probabilities are all 0 or 100 ("decided") shows a summary instead of the ranking (champion, runner-up, promoted, relegated; for Série D the expand button lists the clubs that secured Série D 2027 through the third phase and the 64 eliminated).

**Série B/C next phase in `LeagueSim`** (v4.84). The Monte Carlo and "1 Simulação" tabs each have a sub-view switch "Fase de liga | Playoff de acesso" (B) / "Quadrangular + final" (C). The MC view (`LeagueNextPhaseMC`) reads `rMC.probs` (`g4`, `bPlayoff`, `bAccess`; `q4`, `qFin`, `qChamp`, `matchups`) and the locked seeds from `bcSeeds`; the 1 Sim view (`LeagueNextPhaseSU`) renders `rSU.fase2`, which `simUnica` now returns from `simFase2BC` (playoff legs and aggregates, or both quadrangular groups with their 12 games, standings, final and champion), with official scores and user edits marked. `bcSeeds` computes the mathematically locked positions over `BC_RES_MERGED` (embedded + `results.json` + manual results, assigned by `SimuladorUnificado` inside the `mergedRes` memo) — before v4.84 `refreshBcUser` and `LeaguePhaseEdit` looked only at the embedded `SB_RES`/`SC_RES`, so Série B (embedded through round 16) never locked a seed and the playoff edits never reached the MC. `BC_USER.Bsc` keeps the edited playoff scores next to the winner map `BC_USER.B`.

**Série B access playoff — real fixture** (v4.95). `results.json.po_b` carries the CBF's playoff fixture (4 rows: `leg` ida/volta, `data`, `casa`, `fora`, `gc`/`gf` null for an unplayed leg, `pen_c`/`pen_f`); `applyPoBAuto` turns it into `PO_B_AUTO` (`ties` = the two real pairings, `legs['casa>fora']`), accepted only when it is exactly 2 ties between 4 distinct clubs. Three functions are the single source for everything downstream: `poBPairs(po4, usarReal)` gives the pairings for the simulated 3º–6º — the **real** ones when those four clubs are the published four (so the bracket does not depend on the app reproducing the 3º–6º order exactly), otherwise the presumed 3º×6º / 4º×5º; `poBTie(a, b, legSim, usarReal)` resolves one tie leg by leg with precedence **real score > complete user edit (`BC_USER.Bsc`) > Poisson**, real mando when published (never assume the ida is at the worse side's home — same lesson as the Série D `SD_KO_CODES`), and for a tied aggregate real penalties > the user's pick > coin; `ligaCompleta(tab, res)` gates all of it, so in the Evolução per-round truncation the playoff does not exist yet. `simMC_single` (via `extraStats.__poB`), `simFase2BC`/`simUnica`, `refreshBcUser`, `LeagueNextPhaseMC` (shows each leg with date and official score, and warns when the CBF's pairings do not fit this browser's 3º–6º), `LeaguePhaseEdit` (`realAB[k]` locks the fields already played — the same mechanism the Série C final uses) and the Config log (`PO·i`/`PO·v`) all go through them. Before v4.95 the app drew both legs from scratch even after the first legs had been played.

**Official results replace what the browser stored** (v4.95). `handleSearchResults(results, {oficial: true})` — the `results.json` load — now *replaces* a stored score for the same game (`mergeFetchedRes`); local sources (the PDF panel / pasted JSON) still never overwrite. Until then the merge into `localStorage['simUni_fetchedRes']` was first-wins on both sides, so a correction published in `results.json` never reached a browser that had already stored the old value: Fortaleza 1×0 Operário-PR (R25 of B, corrected to 1×1 on 27/09) stayed forever, gave Fortaleza 67 points instead of 65 and flipped the playoff pairings. The documented precedence **embedded > manual > fetched is unchanged**: a score typed in the Jogos tab still outranks the official one until the user clears it — if a table is wrong in one browser only, `simUni_userRes` is the next suspect.

**Copa do Brasil 2027** (v4.86). The Copa BR tab's "2027" sub-tab (`CopaBrasil2027`) shows who already has a 2027 slot, the entry phase and the open slots. Rules come from the Copa do Brasil 2026 REC (Art. 2º and §17, which already writes the 2027 version): 128 clubs; Série A 2027 → 5ª fase; champions of Copa do Nordeste, Copa Norte, Copa Centro-Oeste, Copa Sul-Sudeste, Série C and Série D 2026 → 3ª fase; 102 state slots called down each state championship's general classification, skipping Critério 1/2 clubs, with state cups taking the last slots. The 1ª/2ª fase split (66 best Critério 3 clubs in the RNC 2027 go straight to the 2ª) is derived from the phase sizes, not written in any REC, and uses the projected RNC until the official one (December). Data lives in `CB27_UF` (per-state classification + cups, `src` 'C' confirmed / 'I' partly inferred), `CB27_REG` and `CB27_NAC_D`, researched on 27/09/2026; homonyms from another state carry a UF suffix (`Cruzeiro-AL`, `Barcelona-BA`…), and at load time the block fills `UF_MAP` for names that have no UF yet (same pattern as `SD_INFO` → `UF_MAP`), so `TN` shows the discreet state label. A state cup still undecided is rendered as its own "❓ a definir" row with its date and contenders; the "Só vagas em aberto" toggle hides guaranteed clubs and lists, per state, the cascade slots with each contender's chance of a state slot. When a state cup or a regional is decided, update those constants and the changelog — nothing in the automation feeds them. `buildCB2027(dash, rncProj, resA, resB)` samples Série A 2027 and the C final jointly per draw from three traces `simMC` now records: `A.rebTrace` (for A the extraStats object carries only this; the B/C per-state block stays off), `B.accTrace` (top 2 + playoff winners) and `C.finTrace` ([champion, runner-up]). "Garantido" is a points rule, never Monte Carlo.

**Simulation engine** (pure functions, no React): `poissonProb` → `calcProbs`/`calcL` (Poisson goal expectations from Elo + atk/def), `updR` (Elo + atk/def update after a game), `applyDrift`/`boxMuller` (per-sim structural-uncertainty noise on Elo and atk/def), `initLeague`/`computeCurrentAD`/`backtestSeries` (derive current team strength from real results played so far), `simMC` (N-run Monte Carlo, 1k or 10k) and `simUnica` (single deterministic-ish run). Each series has special post-season logic: Série B access playoff (3º–6º), Série C final quadrangular (G8 → 2 groups → final ida/volta), Série D's large multi-phase knockout handled via `prepareSerieDState` + `pairKey` (matches results to fixtures by sorted-pair+leg, not exact home/away/round). Série D 2026 promotes **6**: the 4 semifinalists plus the 2 winners of the **play-off de acesso** (`SD_PO_PAIRS`: F03 = loser E01 × loser E02, F04 = loser E03 × loser E04 — bracket-structured, NOT reseeded). Since v4.79 the knockout pairing/mando precedence everywhere (MC, 1 Sim, bracket, Geral) is: real CBF codes from `ko_d` (`SD_KO_CODES`, `a` = actual ida host) > `paresConhecidos` (legacy, phase-blind) > presumption (campaign reseed / `ordIda`). Never assume the ida host is the worse-campaign side — the CBF broke that rule in D04 and E02 and both flips flipped penalty winners (the "Iguatu advances" bug).

**Evolução tab** (v4.80). `EvolucaoSim` re-runs the Monte Carlo at every point of a time axis
"as if" only the results known up to that point existed, and plots one team's metric. For
A/B/C the axis is rounds 0..maxR and the mechanism is just `mergedRes[sk].filter(r => r.r <= N)`
— `simMC_single` decides played-vs-simulated purely from the `res` array, so no engine change
is involved. For Série D and Copa do Brasil the axis is knockout phases, driven by an optional
trailing `opts` argument on the engine entry points: `simMC`/`simMC_async` take
`{ignoreUser}` (clears `BC_USER`), `simMC_D`/`simMC_D_async` take `{koMask}` (a Set of phase
letters B..G whose real results may be used; `s180` receives the phase letter at each call
site), `simMC_CB` takes `{cbMask}` (a Set of `'R32'`/`'R16'`). `null`/absent = the old
behaviour. `SD_KO_CODES` is deliberately *not* masked (it is bracket structure, not a result).
One sweep stores scalar metrics for every team, so switching team/metric never recomputes;
the cache and progress live in `SimuladorUnificado` (tabs unmount on switch) and a sweep is
mutually exclusive with "Simular Tudo" because the `BC_USER` reset is global. Known uniform
leaks: `applyCBToLeague` feeds Copa do Brasil legs into the initial Elo at every point, and
the Copa sweep uses the current dashboard's evolved strengths at every point.

**Ranking Nacional de Clubes** (v4.66–v4.70). `RNC_2026` holds the CBF's published 2026 table
(235 clubs) plus `s5` = Σ(P2021..P2025), which the CBF does *not* publish — it is reconstructed
from the league and Copa do Brasil classifications of those years by `scripts/rnc_data/` (see
its README). The check that matters: `5·P25+4·P24+3·P23+2·P22+1·P21` reproduces the published
value for all 235 clubs with no divergence, which validates the points scale, the parsing and
the name reconciliation at once. `buildRNC` projects 2027 (`RNC2026 + 5·P26 − s5`) with P26 from
the Monte Carlo. The **`rnc` tab** renders it.

**Série D 2027** (v4.68–v4.70). `EST_FILA_2027` is the per-state succession queue. Two rules for
a vacated state slot, with *opposite* destinations — swapping them yields a plausible, wrong
table: a club that **is promoted to Série C** frees its slot to the next in the *same state*;
a club with a **double slot** (state + Critério 3) sends the surplus to the *Ranking Nacional*
and the state gains nothing. `build2027Alloc` applies the four criteria of Art. 2º of the REC
per draw, coupling the C and D simulations through the traces. `sorteio2027` projects the 16
groups as a min-cost flow where the max-3-per-state cap is the **arc capacity**, so an invalid
group is unrepresentable rather than repaired. All of it lives in the Série D `cl27` sub-tab.

**Estados 2027** (v4.91). The `uf27` tab (`Estados2027Sim`) shows, per state, the expected number of clubs in each national division in 2027 and the full distribution P(exactly k): a "Resumo" matrix (UF × division) plus one P(k) table per division; opening a state lists its clubs with the chance of each division. `buildUF2027(dash, rncProj)` builds all four divisions **per draw** — A27 = A26 − 4 relegated + 4 from B; B27 = B26 − 4 − 4 + 4 from A + 4 from C; C27 = C26 − 4 − 2 + 4 from B + 6 from D (24 clubs); D27 = the 96 slots of `build2027Alloc` — because P(k) is a joint quantity: two clubs of one state in the same playoff tie or relegation fight are not independent, and summing per-club marginals only gives the mean. It needs two traces added for it, `B.rebTrace` (4 relegated per sim) and `C.accTrace` (top 2 of each quadrangular group), next to the existing `A.rebTrace`/`B.accTrace`/`C.rebTrace`/`D.trace`. A and B are paired with the D draw by index (`d % n`, series are independent in the model — same argument as `buildCB2027`), so with equal sim counts the per-state expectation reproduces the dashboard's `z4`/`bAccess` with no resampling noise. Série C must use the **same** C draw `build2027Alloc` paired with that D draw — otherwise a club relegated from C would leave C27 in one scenario and enter D27 in another — which is what the optional `cfg.onDraw(d, j, reb, prom, cnt)` hook on `build2027Alloc` is for; the hook does not touch the waterfall or its PRNG, so the Série D numbers are identical to the `cl27` sub-tab. Inherited limit: Critério 4 walks the *projected* RNC 2027 as a fixed order, so the per-state Série D count only varies with promotions/relegations and pending state cups. Slots without a known owner count for the state but have no club row (the panel says so).

**Estados: history, records and sums of divisions** (v4.93). The tab has three views — "Resumo", "Distribuição 2027" and "Histórico" — and the last two take **any sum of divisions** through four A/B/C/D toggles (state `combo`, e.g. `'ABC'`). `buildUF2027` therefore counts, per draw, all 15 combinations by bitmask (A=1, B=2, C=4, D=8; names in `UF27_COMBOS[m]`), because a sum such as A+B+C is itself a joint quantity and cannot be rebuilt from the per-division histograms; each `ufDist` row carries one `{E, pcts}` per combination and `tot` survives as an alias of `ABCD`. `UF_HIST` holds the number of clubs per state per season as digit strings — Série A from 2003, B from 2006, C and D from 2009, through 2025 (`UF_HIST_FIM`) — and **2026 is deliberately not in it**: it comes from the app's own lists (`n26`), so history and simulator can never disagree about the current season. A sum of divisions uses the shortest window (`ufHistY0`). `ufHistSerie` → `ufHistRec` (min/max with the years, and the probability of 2027 landing above, at or below them) → `ufHistSelos` (▲ recorde, ▼ novo mínimo, =máx, =mín; a tie only becomes a badge when the value is above zero and the history is not constant). Records and minimums are in **absolute number of clubs**, not share — the Série D went from ~40 to 68 (2016), 64 (2022) and 96 (2026) clubs, so nearly every state is at its Série D maximum for structural reasons; that is what the "edição" row of the Histórico view is for. The state is the **federation** the club plays under, not the city's (Luziânia is in Goiás and plays in the DF). Source: each season's English-Wikipedia page, every column checked against the edition size; the 2016–17 Série D pages do not give each club's state and five clubs had to be corrected against the group tables (listed in the `UF_HIST` comment), and a second full reading of Série D against another source was not done.

**Points × position** (v4.94). Under the team × position heat map, the Monte Carlo tab of A/B/C (`LeagueSim`) has a second collapsible block, `PtsPosMatrix`: the same reading keyed by **final points** instead of team, in two directions behind a toggle. "Por pontos → posição" is a heat map with one row per points total and one column per position — of every team-in-a-simulation that finished on p points, the share that ended in each position (the row sums to 100) — plus two summary columns, the chance of finishing in the G zone (`meta.zonas.g4`) and in the relegation zone (`meta.nReb`) on that total; rows with fewer than max(10, 0.5% of nS) cases are dimmed, and totals no simulation produced collapse into a `⋮` gap row. "Por posição → pontos" is one row per position with median, p10–p90 and one heat chip per points total (the share of simulations in which whoever finished there had that total). It is deliberately a list and not the transposed matrix: points as columns means up to ~100 columns and the relegation rows permanently off-screen, on a phone and on a desktop. Both are the **same joint count with different denominators**: `simMC_finalize` condenses the `ptsAtPos` samples it already kept for `cortes` into `rMC.ptsPos = {lo, hi, nS, m}` (`buildPtsPos`; `m[p − lo][pos]` = simulations in which position `pos` finished on `p` points, so every column sums to nS), `ptsPosAxis` builds the descending axis with `null` gap markers, and `ptsPosPctl` applies the percentile rule of `cortes`, so the two can never disagree. It is the "any team" reading — the 42-point row pools every club that can reach 42, weighted by how often each does — not a per-club conditional. No draw changed (no PRNG impact) and the Evolução sweep keeps none of it (`evoReduce` reads only `probs`). **Série D** (v4.96) has the same block in its own Monte Carlo tab, before "Visão por Grupo": group-stage points × position **within the group** (1º–6º), the 16 groups pooled, with "Avança" (top 4) and "Elim." as the summary columns. It is the same component with its labels passed in (`rot`); the data is `rMC.ptsPosGr`, counted directly in `simMC_D_single` into `gpts.pp` (a count, and all six positions — `gpts` itself only keeps samples for the first four) and shaped by `ptsPosFromCounts`. The sample per position is nS × 16, since every simulation has 16 groups. With the group stage over it is the real distribution of the 16 groups of 2026.

**Continental berths — dynamic line** (v4.98). The Série A Monte Carlo tab opens with `VagasIntPanel` ("Vagas continentais 2027 — linha dinâmica"): for every simulation the berths are handed out from the simulated table **and** the cups, so the line (G6/G7/G8) is a distribution, not a constant. `alocaVagasInt(ord, nReb, base, lib, sul, cdbCh, cdbVi)` is the pure rule: league 1º–4º group stage and 5º preliminary (`VAGAS_INT.base`); Copa do Brasil champion group stage, runner-up preliminary; if the champion already has a direct berth the direct one goes to the runner-up and the preliminary one goes down the table; the berth of a finalist that is already qualified **or relegated** goes down the table; a Brazilian Libertadores/Sul-Americana champion enters outside the quota; the Sul-Americana takes the next 6 eligible clubs. Those rules come from **press summaries** of the Série A 2026 REC (Art. 6º/7º) and the Conmebol manual — the REC text itself was not read; the four published 2026 scenarios are reproduced by the harness. Known unconfirmed point: a continental champion that is relegated loses the berth with no hand-down. The Copa do Brasil finalists come from the automation (`cdbFinalInfo` reads `CB_AUTO.ko.F`); while the final is unplayed and its two orders would give different results, each draw counts both with weight ½ (`vi.cdbPesa`) — in 2026 the order changes nothing. **A continental final is never drawn, it is weighted**: `VAGAS_INT.lib`/`.sula` hold the final, its Brazilian club(s), `campeao` and `p` — the **assumed** chance of `final[0]` lifting the trophy (the app has no rating for the foreign side; `lib.p = 0.65` is the eve-of-final champion market, 1.43 × 2.60 with the margin removed; Opta's model said 59%). While `campeao` is null and a Brazilian is in it, `vagasIntCtx` opens one scenario per outcome (at most 4), each with `peso` = the product of the assumed chances (no `p`, or one outside 0–1, means ½). `simMC_single` counts every scenario in the same draws (`extraStats.__vi` → `rMC.vagasInt`, Série A only; no PRNG impact), and the panel shows **one table**: `vagasIntComb(vi, vagasIntPesos(vi, p))`, the scenarios averaged by those weights — exact under the model, where the final is independent of the league table, and with no extra Monte Carlo noise. The slider in the panel changes the chance for that browser and only redoes the average, never the simulation; "Ver por cenário" opens the scenarios side by side, each with its weight. From 59% to 65% no club's Libertadores chance moves more than 2 p.p. The chance does **not** touch the "time sem objetivo" cuts, which keep every cut that is still possible. **`VAGAS_INT.<final>.campeao` is hand-maintained** — nothing in the automation feeds it; when a final is decided, set it and add a changelog line. Until then the panel's buttons let one browser inform the result and re-run through `manualTick`. Both live in `localStorage['simUni_vagasInt']` — `{"lib":"Estudiantes"}` for an informed result (an official `campeao` always wins), `{"p":{"lib":0.5}}` for a changed chance. Not changed: `SA_META.zonas` — the G4 / 5–6 / 7–8 colours and labels of the tables are still the fixed ones — and the Evolução sweep, which uses today's knowledge of the cups at every point.

**Time sem objetivo** (v4.98). `cfg.semObj = {on: true, m: 1.15, ultimas: 8}` (card `SemObjCard` in Config; `cfg` is not persisted, so the switch lasts for the session). In the last `ultimas` rounds of **Séries A and B**, before each simulated round `semObjFlags(st, cortes, nR)` marks a team as having nothing to play for when it is *decided at every cut* — it has already guaranteed the top-k or can no longer reach it, by points arithmetic only, a possible tie on points counting as a threat (the rule errs towards not flagging). In a game between a flagged and an unflagged team the flagged side's λ is divided by m and the opponent's multiplied by m, after `calcL` — so it works the same in ATK/DEF and in Elo-only mode — with the same clamps as the draw. The cuts are `SEM_OBJ_ATUAL[sk]`, refreshed by `refreshSemObj` next to `refreshBcUser` at the three simulation entry points: Série B fixed at `[1, 2, 6, 16]`; Série A from `semObjCortes`, i.e. title, relegation and **every continental cut still plausible** given `VAGAS_INT` and the Copa do Brasil final (today `1,4,5,6,7,8,11,12,13,14,16`) — a club that can still cross a line that may come to exist keeps its objective. Séries C and D have no cuts and are never adjusted (the historical evidence for the C first phase is inconclusive). Flags are recomputed inside each simulation, so a club that becomes decided in simulated round 37 is flagged in round 38 of that draw. Evidence: Série A 2006–25 −0.23 point per game against expectation (odds ratio 0.68, 18 of 20 seasons negative), Série B 2012–21 −0.19, five European leagues −0.14; m = 1.15 ≈ −0.2 point per game. **It acts only on simulated games**: ratings (`updR` only runs after a real game, which the adjustment never touches), `backtestSeries`, the calibration tab and Confronto do not see it. With `on: false`, or m = 1, the engine is bit-identical to v4.97. `eval/sem_objetivo.cjs` measures on × off.

**Per-series data** is hardcoded as `S{A,B,C}_TAB` (fixtures), `_RES` (real results played), `_RANKING`, `_DATES`, `_NM`, plus `_META` objects (e.g. `nReb` relegation count, zone cutoffs — these encode 2026 CBF format changes like Série C having only 2 relegated). Copa do Brasil uses `CB_RES_IDA`/`CB_RES_VOLTA` for the round of 32 and `CB_R16_PAIRS` for the (drawn) round of 16. Since v4.84 the bracket from the quarterfinals to the final is also real: `applyCbAuto` turns the `QF`/`SF`/`F` rows of `results.json.cb` into `CB_AUTO.ko` (ties in the same `{a, b, sc: {g1a, g1b, g2a, g2b}, pen}` convention as the round of 16, `a` = first-leg host) plus `CB_AUTO.sfLinks` (which quarterfinal feeds each semifinal, resolved by name once the PDF lists the semifinalists). `cbKoPlan(r16winners, cbMask)` is the single place both `simMC_CB` and the tab's `runBracket` ask for that structure: the real quarterfinal pairings are used only when the eight simulated round-of-16 winners are exactly the real eight (otherwise the old per-simulation draw), semifinals follow `sfLinks`, real scores enter per phase mask, and — like `SD_KO_CODES` — the pairings themselves are never masked. The 2026 edition draws the whole bracket at the quarterfinal stage (GR 119 Inter×Grêmio, 120 Cruzeiro×Atlético-MG, 121 Vasco×Vitória, 122 Palmeiras×Santos; semis 123/124; final GR 125 on 06/12), so "sorteio a cada fase" no longer describes it. The Evolução Copa axis gained "Após quartas"/"Após semis"/"Após a final" points (masks `QF`/`SF`). Results are merged with user-fetched results from `localStorage`.

**`UpdaterPanel`** ingests new real results: it downloads a CBF PDF through the `allorigins.win` CORS proxy, then calls the Anthropic Messages API (`api.anthropic.com/v1/messages`, model `claude-sonnet-4-6`) with the PDF as a document block to extract finished matches as a JSON array, which is merged and persisted. API key resolution order: `window.__ANTHROPIC_API_KEY__` (build-time placeholder `__ANTHROPIC_API_KEY__`, optionally replaced by a CI secret) → `localStorage['simUni_apiKey']` → manual entry. There is a fully manual fallback ("Copiar prompt" + paste JSON) when no key/proxy is available.

**`AtualizarPanel`** (v4.89, the "📡 Atualizar" button next to "Simular Tudo", which replaced the old client-side "🔍 Buscar" web search) triggers the results Action on demand: `workflow_dispatch` of `update-tables.yml` through the GitHub REST API, then polls the run (queued → current step → conclusion), checks `GET /commits?path=results.json&since=<run start>` to tell "new results" from "CBF hasn't republished", and polls `results.json?t=` until the Pages copy has `updated_at` ≥ run start before offering a reload. If a run is already queued/in progress (e.g. the scheduled one) it tracks that run instead of queueing another. Auth is a fine-grained GitHub token (this repo only, Actions: read and write) kept in `localStorage['simUni_ghToken']` — per browser, never in the repo; without it the panel shows the last run and links to the Action's "Run workflow". The step labels map the workflow's step names in `GH_PASSOS` — rename a step in the YAML and the label falls back to the raw name.

**Clearing typed scores** (v4.97). The Config tab has a "✎ Placares digitados neste navegador" panel (`ManualResPanel`, between `SettingsTab` and the automation log): it lists what this browser holds per origin (`manualResSummary`) and a "Limpar todos os placares digitados" button with an in-page confirmation (no `window.confirm`). `clearManual` zeroes `userResAll` and removes the keys in `MANUAL_LS` — the single list of typed-score keys other than `simUni_userRes`; a new editor's key goes there. It does not touch `simUni_fetchedRes`, `simUni_est27` or the API key/token. The per-tab clear buttons are still there.

**Automatic result updates** (added separately from the app source): a twice-weekly GitHub Action (`.github/workflows/update-tables.yml`, crons `0 14 * * 1` and `0 9 * * 5` — Monday 14:00 UTC / 11:00 BRT and Friday 09:00 UTC / 06:00 BRT — plus manual dispatch) on the repo `agamemnon140/brasileiro-2026` runs `scripts/fetch_tables.mjs`: it discovers the current official CBF "Tabela Detalhada" PDFs via the public Strapi CMS (`cms.cbf.com.br/api/championship-documents`, type "Complemento de Tabela" — the blob URL hash changes weekly; since v4.84 only a document titled "Tabela Detalhada" is accepted: in September 2026 the CBF removed the Séries C and D detailed tables from the CMS and left only the "Tabela Básica", a fixture list with no scores, which the old `/tabela/i` filter happily picked — 0 results extracted and the PDF cache pointing at a score-less PDF. Now the run warns and skips that série with the cache untouched. Since 27/09 the **Série C second phase no longer depends on the PDF**: `fetchQuadCGweb` reads the CBF site's own match API ("GWEB", `https://www.cbf.com.br/api/cbf/jogos/campeonato/<edition>/rodada/<n>/fase`, editions in `GWEB_EDITION`: A 1260611, B 1260612, C 1260613, D 1260635, Copa 1260615, taken from `/api/cbf/campeonatos/anos`), which returns every phase's games for round n with score (`gols` null when unplayed), date and per-side penalties, and feeds the same `mergeQuadRows` merge before the PDF loop on every run at no API cost. `QUAD_GWEB_DRY=1 node scripts/fetch_tables.mjs` (with `NODE_EXTRA_CA_CERTS=scripts/cbf-ca.pem`; the site shares the CMS's incomplete Sectigo chain) prints what it would ingest. The same API also feeds the **league phase of A/B/C** (`fetchLigaGweb`, first phase only for C — group "GRUPO A"; per-série name maps in `GWEB_NORM_S`, since "Botafogo" is Botafogo-RJ in A and Botafogo-SP in B), and unlike every other source it is **authoritative**: it runs before the PDF loop and, when a recorded score differs, it overwrites it with a `::warning::Corrigido pela API da CBF` line and a `corrigido_de` field on the row (`last_run.corrigidos` counts them). That exists because the PDF-plus-model extraction once stored Fortaleza 1×0 Operário-PR (R25 of B; official 1×1) and the never-overwrite rule would have kept it forever. Games that started less than 3 h ago are skipped (a live match shows a partial score). `LIGA_GWEB_DRY=1` prints, per série, new games and scores that would be corrected. Since v4.95 the league pass skips the Série B group whose name matches `/PLAYOFF/i`: the API lists the **"PLAYOFF DE ACESSO" as one more group of the B edition, in rounds 1 (ida) and 2 (volta)**, and the first legs share the `casa|fora` key of two league games (R22, R24), so every run "corrected" those two league scores to the playoff scores and back — 4 corrections per run, `results.json` rewritten with no news, the final state right only because of the order the rounds are read in. Those games go through their own pass, `fetchPoBGweb` → `results.json.po_b` (whole fixture, score null while unplayed or still inside the 3 h window; the API is authoritative here too; `last_run.po_added` counts in `total_new`; `PO_GWEB_DRY=1` prints it). Only the D knockout and the Copa do Brasil still depend on the PDFs), downloads them (cms.cbf.com.br serves an incomplete TLS chain, hence `NODE_EXTRA_CA_CERTS` pointing at the vendored `scripts/cbf-ca.pem`), extracts played league-phase results with the Anthropic API (PDF document block) and merges them into `results.json` at the repo root, committing on change so GitHub Pages redeploys. Since v4.59 it also covers the **Série D knockout**: the D PDF's mata-mata legs (GR code + ida/volta + penalties) go into the `ko_d` field of `results.json`, which the app converts into `SD_KO_AUTO`/`SD_KO_PART_AUTO` overlays (precedence: user edits > hardcoded > automation) feeding the MC, the bracket defaults, the Geral tab and the Config log. Since v4.64 the Copa do Brasil round of 16 goes into `cb` (`applyCbAuto` → `CB_AUTO`, user edits win); since v4.84 the same pass extracts everything from the round of 16 onward as one row per leg (`fase` R16/QF/SF/F, `gr` = CBF tie number, `leg` ida/volta, `data`, `pen_c`/`pen_f`, `gc`/`gf` null for an unplayed game — that is how the app learns the bracket before a phase is played; round-of-16 rows still require a score and a real `CB_R16_PAIRS` pairing), keyed by `fase|casa|fora`, never overwriting a recorded score, and `cb_added` now counts in `total_new`. The final is a single game in the app's model, matching the one row (GR 125, 06/12) in the CBF table. Since v4.81 the **Série C second phase** goes into `quad_c`: the C PDF gets a third extraction pass that returns the whole quadrangular fixture (CBF groups B/C, rounds 1–6, plus the final once its teams are known) with `gc`/`gf` null for unplayed games, so the app knows the real group composition before round 1; `applyQuadCAuto` turns it into `QUAD_C_AUTO` (groups in CBF-letter order → app groups A/B, per-game scores, final legs with penalties). **The final arrives in two shapes**: the PDF pass writes `fase: 'FINAL'`, but the GWEB API has no such phase — it lists the final as one more group, "GRUPO D", rounds 1 (ida) and 2 (volta), stored as `fase: 'Q', grupo: 'D'`. Since v4.92 `applyQuadCAuto` therefore also recognizes the final by structure (a "group" of exactly 2 clubs, one from each quadrangular; letters in `QUAD_C_AUTO.finalG`, single test `quadCIsFinal(r)`, also used by the Config log). Before that the two legs of the real 2026 final sat in `results.json` for a month as phantom group games (`n` = 26, `final` = {}), the Monte Carlo kept drawing a decided title, and the `cb_ko` harness — which compares locked group games with `QUAD_C_AUTO.n` — kept the Action red from 19/10. The scraper deliberately does **not** convert those rows to `FINAL` (merge key is `fase|casa|fora`, so it would duplicate them); known limit: `sanitizeQuadC` keeps penalties only on `FINAL` rows, so a GWEB final decided on penalties would arrive without them. The C MC uses the real groups only when the simulated top-8 equals the real one (`quadCRealGroups`), so the Evolução per-round truncation keeps the presumed 1-4-5-8 / 2-3-6-7 split; real scores take precedence over user edits (unlike `ko_d`), and `LeaguePhaseEdit` locks played games. When the C PDF URL is cached but `quad_c` is still empty, the run downloads the PDF and does only that pass. `last_run.quad_added` is part of `total_new`; the Config log lists those games as série C with round `Q<grupo><rodada>` or `F·i`/`F·v`. It skips games already hardcoded in the app by parsing `SA/SB/SC_RES` (and `SD_F2_REAL`/`SD_F3_REAL` for D — keep those parses updated when consolidating new knockout phases) out of `index.html`. The app loads `results.json` on mount via a `useEffect` (injected just after `handleSearchResults` in `SimuladorUnificado`, in both `index.html` and `brasileirao-2026.html`), feeds it through the same `handleSearchResults` pipeline, and the dashboard auto-run waits for that fetch to settle (v4.55c). Server-side guardrails: canonical-team allowlist + `NORM_NAME` map (kept in sync by hand with the app team lists), score range 0–14, round 1–38, never overwrites a recorded score (logs conflicts), per-run volume cap. An earlier web-search-based Action (`fetch_results.mjs` + `update-results.yml`, Anthropic `web_search` tool) was retired in favor of the official PDFs — see git history if it's ever needed again. The Action needs the repo secret `ANTHROPIC_API_KEY`; the API key is never exposed client-side here.

**Reading the automation's output correctly.** The envelope carries a `last_run` block (`{at, added, ko_added, total_new}`) recording what **that run** contributed. The badge under the app title shows that delta — `📡 Tabelas CBF atualizadas em <data> · +N novo(s) nesta atualização` — and keeps the cumulative total in its `title` tooltip; the Config tab still lists the cumulative figure, labelled "acumulados". Envelopes written before `last_run` existed fall back to the old cumulative wording, so both shapes render.

Because the writer returns early when nothing changed, `results.json` is only rewritten on a real change: `updated_at`/`last_run` always describe the last **effective** update, and a no-op run leaves the badge showing the previous one. That is intended — but it means the badge alone cannot tell you whether this week's run executed. Check the Action for that. A run legitimately adds nothing when the CBF has not republished that série's PDF (the discovered blob URL is unchanged from the previous week), so "no new results" is an expected mid-week outcome and is not evidence of a broken key or exhausted credits. Real API failures surface as a failed step in the Action, not as a silent empty diff; `gh run view <id> --log` and its `Resumo: +X liga + Y mata-mata D novos, ...` line are the ground truth for any given run.

## Prediction evaluation (`eval/`)

`eval/` measures how well the model actually predicts — short term (per-match V/E/D,
walk-forward) and long term (projected table via Monte Carlo). Run it with
`node eval/run.cjs`; see `eval/README.md` for the design and `eval/REPORT.md` for the
current findings.

**`eval/` only ever READS the app.** It slices the engine out of `index.html` in memory
(via the pre-existing `scripts/engine.cjs`) and writes only to `eval/out/` and
`eval/REPORT.md`. It never edits the app and never runs `build_html.js`. `run.cjs` aborts
if the checkout is behind `origin/main` or if `index.html`/`results.json` are dirty —
evaluating a stale copy measures a model that is not live, which this file already warns
about above.

Two findings from `eval/` change how the config should be read, so they belong here:

- **`kElo` and `homeAdv` do not affect predictions** in the mode the app runs (`eo=false`,
  ATK/DEF — `dashEo` defaults to `false` and the UI labels it "default"). `calcL` computes λ
  purely from `atk`/`def`; `updR` evolves Elo and atk/def on separate tracks and the running
  Elo never feeds back into λ. Measured, not inferred: Brier delta is *exactly* zero for
  `kElo` 16→64 and `homeAdv` 100→400, in all four series. The only channel for prior
  strength is the **initial** Elo, through `initLeague → initAD`. Do not "tune" those two
  parameters expecting predictive change — and note `backtestSeries` is called without the
  `eo` argument, so the app's own calibration tab always measures ATK/DEF regardless of what
  the dashboard is running.
- **`targetRatio` is only live for Série A.** `initLeague` computes
  `rawSpread = log(targetRatio)/log(maxElo/minElo)` and caps it at `maxSpread` (5). Séries B,
  C and D have narrow initial-Elo ranges, so `rawSpread` is 8.9–47 and the cap binds — their
  Brier is bit-identical across `targetRatio` 1.5→8.0. Only Série A (rawSpread 4.54) sits
  below the cap and responds. The parameter looks global and is not.
- **What the seed transmits is mostly SPREAD, not ordering.** Rescaling every seed to a
  common range and then shrinking it by a factor `k` produces a U-shaped Brier curve in every
  série, and at the optimum the orderings ("by hand", RNC, previous year) converge to nearly
  the same value. Série A currently runs at k≈1.06 against a measured optimum of 0.35–0.50 —
  it is the one série whose seed spread is wrong, and also the one with the significant home
  bias. B (k≈0.17) and C (k≈0.09) are already near their optima. Full tables in
  `eval/REPORT.md` §3.
- **The home-advantage bias tracks `lambdas[serie].pesoCasa`.** Séries A (0.652) and D
  (0.604) over-predict home wins by 9.1 and 5.6 pp respectively, both statistically
  significant; B and C (0.583) are within noise. Before changing `pesoCasa`, check the
  observed split in `eval/out/curto.json`.
- **The "time sem objetivo" adjustment was not tuned on 2026** and 2026 cannot judge it.
  `eval/sem_objetivo.cjs` (on × off on the live engine, nothing patched) finds 23 flagged
  games in A+B: 0.74 real points per game against 0.83 expected, and 0.66 expected with
  m = 1.15 — same direction as the 20-season finding, smaller, and well inside the noise
  (Brier on those games −0.035 in A, −0.010 in B, both intervals crossing zero). Do not move
  `m` on that. Since v4.98 the long-term stage also runs with the adjustment on, and with a
  shortened horizon (H < 38) it treats round H as the end — see `eval/README.md`.

**The last two bullets are under review since 14/11/2026: read `eval/REVISAO.md` before
acting on them.** Both were measured on games up to 19/08. On the games played after that
date the candidate config they motivated (`pesoCasa` 0.58, Série A seed shrunk to k=0.4)
scored worse than the live one (`node eval/holdout.cjs`), and the Série A seed ranking
flipped between the round-23 and round-34 horizons. A multi-season study decides; until
then they are hypotheses. The first two bullets (inert `kElo`/`homeAdv`, `targetRatio`) are
code facts and stand. Also since 14/11: `node eval/paridade.cjs` shows the prediction core
is identical in every `index.html` version since 05/06, so for the league tables the replay
the harness measures is what the app published.

**Multi-season update, 15/11/2026** (`eval/hist/`, Séries A–D 2022–2025, 5,592 league games;
details in `eval/REVISAO.md`). Home advantage: one `pesoCasa` of 0.60 for the four leagues
beats the live values per match in 15 of 16 season×série cells, chosen out of sample. Série
A (0.652) over-predicts home wins by 7.5 pp (z = 6) and B/C (0.583) under-predict by 3–5 pp,
so 0.58 is the wrong number for B and C. None of it moves the projected table: in a double
round-robin home advantage cancels, and zone-event Brier is flat. Série D `total` (2.65)
has been about 0.34 goals above reality for five seasons. Preset `base` as the default does
not hold outside Série D. No rule-derived seed (previous table, inherited rating, state
strength, qualification route) beat equal seeds by the pre-registered rule; small spread
(about 90–175 Elo) helps Série A in 3 of 4 years and fades after a quarter of the season.

When `simMC` is called from a harness, pass the **parsed** fixture (`parseTab(SX_TAB, SX_NM,
SX_DATES)`), not the raw `SX_TAB` strings — the raw form silently produces nonsense (100%
title, 0 points) instead of failing.

## Conventions

- The big comment block at the top of `index.html` is a **running changelog** (v4.x). When making a substantive change, add a dated/versioned entry there describing the fix and its rationale — this is the project's primary record of why things are the way they are.
- Series-format rules (relegation counts, access slots, playoff/quadrangular structures) reflect specific **2026 CBF regulations** and have been corrected repeatedly; verify against the regulation before changing zone cutoffs or `nReb`.
- Watch for call-stack overflow: the code uses a `minMax()` loop instead of `Math.min/max(...arr)` because Série D produces very large sample arrays (~960k).
