# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-page React app that simulates the 2026 Brazilian Brasileirão (Séries A, B, C, D + Copa do Brasil) using an Elo + Poisson goal model run through Monte Carlo. It is a PWA (installable, offline-capable) shipped as **one standalone HTML file** with React/ReactDOM/Tailwind pulled from CDNs. UI text is in Brazilian Portuguese.

## Repo

The working repo is named `brasileirao-2026` (same name as the app and its built HTML); this directory is the project root. It is published to GitHub as `agamemnon140/brasileiro-2026` (note the spelling difference) and served by GitHub Pages at <https://agamemnon140.github.io/brasileiro-2026/>.

## Critical: git is the source of truth — sync before doing anything

**Always work from the files as they exist in git, and start every session by syncing.** The GitHub Action commits to `main` on its own (see *Automatic result updates*), so a local checkout goes stale on its own schedule, with no action from anyone. A stale checkout has repeatedly caused false conclusions — reading a `CLAUDE.md` that describes a retired pipeline, or opening a months-old `index.html` next to an empty `results.json` and concluding the automation was broken when it was working fine.

```bash
git fetch origin && git status -sb   # check drift BEFORE reading or editing anything
git pull --ff-only                   # then bring the checkout up to date
```

Before answering any question about the app's live behavior or the automation's output, check what is actually on `origin/main` (`git show origin/main:<file>`, `gh api`, or the Pages URL) rather than trusting the working copy. If the working tree disagrees with `origin/main`, `origin/main` wins — reconcile first, then work. Uncommitted local files whose names do not match anything on `origin/main` are usually superseded leftovers from a rename, not work in progress; check the history before treating them as current.

This applies to `CLAUDE.md` itself: if this file contradicts the code, verify against the code on `origin/main` and fix the file.

## Source layout

The real source is `simulador_unificado.jsx` — a single ~18k-line React component file, tracked in this repo. What the repo contains:

- `simulador_unificado.jsx` — the **source of truth** for all app logic.
- `index.html` / `brasileirao-2026.html` — the **built/transpiled output** (byte-identical; `index.html` is what Pages serves). Do not hand-edit these for logic changes; they are generated (see exception below).
- `build_html.js` — the build script that transpiles the `.jsx` into the HTML.
- `icon_b64.json`, `icon-512.png` — PWA icon assets (base64 icons + favicon, generated by an external `make_icon.py`).
- `results.json` — automation output, **written by the Action, not by hand** (see *Automatic result updates*). Never commit a hand-edited or emptied `results.json`; it will be clobbered by the next run and can mask real results in the meantime.

If you are asked to change app behavior, edit the `.jsx` and rebuild — never hand-edit the transpiled HTML. (Exception: a small, well-isolated value change can be applied directly to the HTML, e.g. the Anthropic model id updated in-place to `claude-sonnet-4-6`. Mirror any such change back into the `.jsx`, or it will be lost on the next rebuild.)

## Build

```bash
npm install @babel/core @babel/preset-react   # no package.json exists; install ad hoc
node build_html.js
```

`build_html.js` does, in order: strips `import React` and `export default` from the jsx; exposes hooks as globals; appends a `ReactDOM.createRoot(...).render(...)` bootstrap; transpiles JSX with `@babel/preset-react` (classic runtime); injects the PWA manifest + icons from `icon_b64.json`; and writes the final HTML. Both paths are resolved relative to the repo via `__dirname` (`simulador_unificado.jsx` in, `brasileirao-2026.html` out), so it builds in place with no path editing. It writes only `brasileirao-2026.html` — **copy it over `index.html` as well**, since Pages serves `index.html`.

There is no test suite, linter, or dev server.

To run the app, prefer the deployed Pages URL. Opening the local HTML works too, but note it fetches `results.json` by **relative path** — so a stale or empty local `results.json` silently yields an app with no automated results, and over `file://` the fetch may be blocked outright. Never diagnose the automation from a locally-opened file; check the Pages URL or `origin/main`.

## Architecture of the app (inside the jsx / transpiled HTML)

Top-level component `SimuladorUnificado` holds a `tab` state switching between: `serieA`/`serieB`/`serieC` (→ `LeagueSim`), `serieD` (→ `SerieDSim`), `copaBR` (→ `CopaBrasilSim`), `h2h` (→ `ConfrontoMerged`), `config` (→ `SettingsTab`). A "Simular Tudo" dashboard is the **single Monte Carlo channel** — individual tabs only keep a "1 Sim rápido" button.

**Simulation engine** (pure functions, no React): `poissonProb` → `calcProbs`/`calcL` (Poisson goal expectations from Elo + atk/def), `updR` (Elo + atk/def update after a game), `applyDrift`/`boxMuller` (per-sim structural-uncertainty noise on Elo and atk/def), `initLeague`/`computeCurrentAD`/`backtestSeries` (derive current team strength from real results played so far), `simMC` (N-run Monte Carlo, 1k or 10k) and `simUnica` (single deterministic-ish run). Each series has special post-season logic: Série B access playoff (3º–6º), Série C final quadrangular (G8 → 2 groups → final ida/volta), Série D's large multi-phase knockout handled via `prepareSerieDState` + `pairKey` (matches results to fixtures by sorted-pair+leg, not exact home/away/round).

**Per-series data** is hardcoded as `S{A,B,C}_TAB` (fixtures), `_RES` (real results played), `_RANKING`, `_DATES`, `_NM`, plus `_META` objects (e.g. `nReb` relegation count, zone cutoffs — these encode 2026 CBF format changes like Série C having only 2 relegated). Copa do Brasil uses `CB_RES_IDA`/`CB_RES_VOLTA`. Results are merged with user-fetched results from `localStorage`.

**`UpdaterPanel`** ingests new real results: it downloads a CBF PDF through the `allorigins.win` CORS proxy, then calls the Anthropic Messages API (`api.anthropic.com/v1/messages`, model `claude-sonnet-4-6`) with the PDF as a document block to extract finished matches as a JSON array, which is merged and persisted. API key resolution order: `window.__ANTHROPIC_API_KEY__` (build-time placeholder `__ANTHROPIC_API_KEY__`, optionally replaced by a CI secret) → `localStorage['simUni_apiKey']` → manual entry. There is a fully manual fallback ("Copiar prompt" + paste JSON) when no key/proxy is available.

**localStorage keys**: `simUni_apiKey`, `simUni_fetchedRes`.

**Automatic result updates** (added separately from the jsx): a weekly GitHub Action (`.github/workflows/update-tables.yml`, cron Fri + manual dispatch) on the repo `agamemnon140/brasileiro-2026` runs `scripts/fetch_tables.mjs`: it discovers the current official CBF "Tabela Detalhada" PDFs via the public Strapi CMS (`cms.cbf.com.br/api/championship-documents`, type "Complemento de Tabela" — the blob URL hash changes weekly), downloads them (cms.cbf.com.br serves an incomplete TLS chain, hence `NODE_EXTRA_CA_CERTS` pointing at the vendored `scripts/cbf-ca.pem`), extracts played league-phase results with the Anthropic API (PDF document block) and merges them into `results.json` at the repo root, committing on change so GitHub Pages redeploys. Since v4.59 it also covers the **Série D knockout**: the D PDF's mata-mata legs (GR code + ida/volta + penalties) go into the `ko_d` field of `results.json`, which the app converts into `SD_KO_AUTO`/`SD_KO_PART_AUTO` overlays (precedence: user edits > hardcoded > automation) feeding the MC, the bracket defaults, the Geral tab and the Config log. Copa do Brasil knockout still ships via versioned app updates. It skips games already hardcoded in the app by parsing `SA/SB/SC_RES` (and `SD_F2_REAL`/`SD_F3_REAL` for D — keep those parses updated when consolidating new knockout phases) out of `index.html`. The app loads `results.json` on mount via a `useEffect` (injected just after `handleSearchResults` in `SimuladorUnificado`, in both `index.html` and `brasileirao-2026.html`), feeds it through the same `handleSearchResults` pipeline, and the dashboard auto-run waits for that fetch to settle (v4.55c). Server-side guardrails: canonical-team allowlist + `NORM_NAME` map (kept in sync by hand with the app team lists), score range 0–14, round 1–38, never overwrites a recorded score (logs conflicts), per-run volume cap. An earlier web-search-based Action (`fetch_results.mjs` + `update-results.yml`, Anthropic `web_search` tool) was retired in favor of the official PDFs — see git history if it's ever needed again. The Action needs the repo secret `ANTHROPIC_API_KEY`; the API key is never exposed client-side here.

**Reading the automation's output correctly.** The badge under the app title reads `📡 Tabelas CBF atualizadas em <data> · N resultado(s) via automação`, where `N` is `results.length + ko_d.length` — the **cumulative total carried by `results.json`**, not the number added by the latest run. To see what a given run actually added, read the run log's `Resumo: +X liga + Y mata-mata D novos, ... já embutidos no app, ... conflito(s)` line (`gh run view <id> --log`), or filter `results.json` by `confirmed_at`. A run legitimately adds nothing when the CBF has not republished that série's PDF — the discovered blob URL is unchanged from the previous week — so "no new results" is the expected outcome mid-week and is not evidence of a broken key or exhausted credits. Real API failures surface as a failed step in the Action, not as a silent empty diff.

## Conventions

- The big comment block at the top of the jsx is a **running changelog** (v4.x). When making a substantive change, add a dated/versioned entry there describing the fix and its rationale — this is the project's primary record of why things are the way they are.
- Series-format rules (relegation counts, access slots, playoff/quadrangular structures) reflect specific **2026 CBF regulations** and have been corrected repeatedly; verify against the regulation before changing zone cutoffs or `nReb`.
- Watch for call-stack overflow: the code uses a `minMax()` loop instead of `Math.min/max(...arr)` because Série D produces very large sample arrays (~960k).
