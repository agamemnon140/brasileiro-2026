# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-page React app that simulates the 2026 Brazilian Brasileirão (Séries A, B, C, D + Copa do Brasil) using an Elo + Poisson goal model run through Monte Carlo. It is a PWA (installable, offline-capable) shipped as **one standalone HTML file** with React/ReactDOM/Tailwind pulled from CDNs. UI text is in Brazilian Portuguese.

## Repo

The working repo is named `brasileirao-2026` (same name as the app and its built HTML); this directory is the project root. It is published to GitHub as `agamemnon140/brasileiro-2026` (note the spelling difference) and served by GitHub Pages at <https://agamemnon140.github.io/brasileiro-2026/>.

## Critical: git is the source of truth — sync before doing anything

**Always work from the files as they exist in git, and start every session by syncing.** The GitHub Action commits to `main` on its own (see *Automatic result updates*), so a local checkout goes stale on its own schedule, with no action from anyone. A stale checkout has repeatedly caused false conclusions — reading a `CLAUDE.md` that describes a retired pipeline, or opening a months-old `index.html` next to an empty `results.json` and concluding the automation was broken when it was working fine.

```bash
git fetch origin && git status -sb   # check drift BEFORE reading or editing anything
git pull --ff-only                   # then bring the checkout up to date
```

Before answering any question about the app's live behavior or the automation's output, check what is actually on `origin/main` (`git show origin/main:<file>`, `gh api`, or the Pages URL) rather than trusting the working copy. If the working tree disagrees with `origin/main`, `origin/main` wins — reconcile first, then work. Uncommitted local files whose names do not match anything on `origin/main` are usually superseded leftovers from a rename, not work in progress; check the history before treating them as current.

This applies to `CLAUDE.md` itself: if this file contradicts the code, verify against the code on `origin/main` and fix the file.

## Source layout — read this before editing app logic

**`index.html` is the source.** There is no build step and no `.jsx` any more.

- `index.html` / `brasileirao-2026.html` — kept byte-identical; `index.html` is what Pages
  serves. This transpiled HTML is the source of truth: it is at **v4.88** and every change
  since v4.48 was made by hand, directly in `React.createElement` form.
- `results.json` — automation output, **written by the Action, not by hand** (see *Automatic
  result updates*). Never hand-edit the `results`/`ko_d`/`cb`/`quad_c` arrays and never commit an
  emptied one: it gets clobbered by the next run and masks real results meanwhile. Envelope
  *metadata* is the one exception — backfilling a newly added field is fine, since the next
  run overwrites it with computed values. Match data, never; metadata with a verified source,
  acceptable.
- `icon_b64.json`, `icon-512.png` — PWA icon assets (generated by an external `make_icon.py`).
- `scripts/engine.cjs` — extracts the pure engine (simulation + data) out of `index.html` so
  headless harnesses can `require` it. See *Verifying changes*.

So: **apply logic changes directly to `index.html`, then copy it over `brasileirao-2026.html`**
so the two stay identical (verify with `md5sum`). Editing transpiled `React.createElement` by
hand is unpleasant but is the only path. Prefer a scripted, assertion-checked patch (count
occurrences, fail on anything but the expected number) over hand-editing a 790 KB file — a
stray match in the Config-tab copy of the same expression is an easy mistake. Known duplicate
anchors: `tab === 'config'` (2), `grupoTop1: 0` (2), `extraStats.__uf = {` (2).

> **Removed:** `simulador_unificado.jsx` and `build_html.js` were deleted once the last
> consumers (the two harnesses) stopped reading them. The `.jsx` had been abandoned at v4.47
> on 2026-06-08 while the HTML moved on to v4.64, so running `build_html.js` would have
> silently regressed seventeen versions — it contained none of the Série D knockout, the
> `results.json` loading, or the Copa do Brasil automation. Git history keeps both if the
> transpiled-source decision is ever revisited.

Run them
  all after touching the engine. `engine.cjs` slices `index.html` from the changelog

  `node scripts/validate_ufdist.cjs` should print `RESULT: PASS`.
- **Screenshots** — `.claude/skills/verify/` documents a headless-Edge recipe. For phone widths, load the test copy inside an `<iframe style="width:375px">`: headless Edge will not open a window narrower than ~480 px, so only an iframe gives Tailwind a real phone viewport (a narrowed `#root` keeps the desktop breakpoints and exaggerates overflow).   `window.fetch` in a scratchpad copy of the HTML is the way to exercise

To run the app, prefer the deployed Pages URL. Opening the local HTML works too, but note it

## Architecture of the app

Top-level component `SimuladorUnificado` holds a `tab` state switching between: `serieA`/`serieB`/`serieC` (→ `LeagueSim`), `serieD` (→ `SerieDSim`), `copaBR` (→ `CopaBrasilSim`), `rnc` (→ `RankingNacionalSim`), `evolucao` (→ `EvolucaoSim`), `h2h` (→ `ConfrontoMerged`), `config` (→ `SettingsTab`). A "Simular Tudo" dashboard is the **single Monte Carlo channel** — individual tabs only keep a "1 Sim rápido" button. Since v4.84 the dashboard card of a série whose probabilities are all 0 or 100 ("decided") shows a summary instead of the ranking (champion, runner-up, promoted, relegated; for Série D the expand button lists the clubs that secured Série D 2027 through the third phase and the 64 eliminated).

**Série B/C next phase in `LeagueSim`** (v4.84). The Monte Carlo and "1 Simulação" tabs each have a sub-view switch "Fase de liga | Playoff de acesso" (B) / "Quadrangular + final" (C). The MC view (`LeagueNextPhaseMC`) reads `rMC.probs` (`g4`, `bPlayoff`, `bAccess`; `q4`, `qFin`, `qChamp`, `matchups`) and the locked seeds from `bcSeeds`; the 1 Sim view (`LeagueNextPhaseSU`) renders `rSU.fase2`, which `simUnica` now returns from `simFase2BC` (playoff legs and aggregates, or both quadrangular groups with their 12 games, standings, final and champion), with official scores and user edits marked. `bcSeeds` computes the mathematically locked positions over `BC_RES_MERGED` (embedded + `results.json` + manual results, assigned by `SimuladorUnificado` inside the `mergedRes` memo) — before v4.84 `refreshBcUser` and `LeaguePhaseEdit` looked only at the embedded `SB_RES`/`SC_RES`, so Série B (embedded through round 16) never locked a seed and the playoff edits never reached the MC. `BC_USER.Bsc` keeps the edited playoff scores next to the winner map `BC_USER.B`.

**Copa do Brasil 2027** (v4.86). The Copa BR tab's "2027" sub-tab (`CopaBrasil2027`) shows who already has a 2027 slot, the entry phase and the open slots. Rules come from the Copa do Brasil 2026 REC (Art. 2º and §17, which already writes the 2027 version): 128 clubs; Série A 2027 → 5ª fase; champions of Copa do Nordeste, Copa Norte, Copa Centro-Oeste, Copa Sul-Sudeste, Série C and Série D 2026 → 3ª fase; 102 state slots called down each state championship's general classification, skipping Critério 1/2 clubs, with state cups taking the last slots. The 1ª/2ª fase split (66 best Critério 3 clubs in the RNC 2027 go straight to the 2ª) is derived from the phase sizes, not written in any REC, and uses the projected RNC until the official one (December). Data lives in `CB27_UF` (per-state classification + cups, `src` 'C' confirmed / 'I' partly inferred), `CB27_REG` and `CB27_NAC_D`, researched on 27/09/2026; homonyms from another state carry a UF suffix (`Cruzeiro-AL`, `Barcelona-BA`…), and at load time the block fills `UF_MAP` for names that have no UF yet (same pattern as `SD_INFO` → `UF_MAP`), so `TN` shows the discreet state label. A state cup still undecided is rendered as its own "❓ a definir" row with its date and contenders; the "Só vagas em aberto" toggle hides guaranteed clubs and lists, per state, the cascade slots with each contender's chance of a state slot. When a state cup or a regional is decided, update those constants and the changelog — nothing in the automation feeds them. `buildCB2027(dash, rncProj, resA, resB)` samples Série A 2027 and the C final jointly per draw from three traces `simMC` now records: `A.rebTrace` (for A the extraStats object carries only this; the B/C per-state block stays off), `B.accTrace` (top 2 + playoff winners) and `C.finTrace` ([champion, runner-up]). "Garantido" is a points rule, never Monte Carlo.

**Simulation engine** (pure functions, no React): `poissonProb` → `calcProbs`/`calcL` (Poisson goal expectations from Elo + atk/def), `updR` (Elo + atk/def update after a game), `applyDrift`/`boxMuller` (per-sim structural-uncertainty noise on Elo and atk/def), `initLeague`/`computeCurrentAD`/`backtestSeries` (derive current team strength from real results played so far), `simMC` (N-run Monte Carlo, 1k or 10k) and `simUnica` (single deterministic-ish run). Each series has special post-season logic: Série B access playoff (3º–6º), Série C final quadrangular (G8 → 2 groups → final ida/volta), Série D's large multi-phase knockout handled via `prepareSerieDState` + `pairKey` (matches results to fixtures by sorted-pair+leg, not exact home/away/round). Série D 2026 promotes **6**: the 4 semifinalists plus the 2 winners of the **play-off de acesso** (`SD_PO_PAIRS`: F03 = loser E01 × loser E02, F04 = loser E03 × loser E04 — bracket-structured, NOT reseeded). Since v4.79 the knockout pairing/mando precedence everywhere (MC, 1 Sim, bracket, Geral) is: real CBF codes from `ko_d` (`SD_KO_CODES`, `a` = actual ida host) > `paresConhecidos` (legacy, phase-blind) > presumption (campaign reseed / `ordIda`). Never assume the ida host is the worse-campaign side — the CBF broke that rule in D04 and E02 and both flips flipped penalty winners (the "Iguatu advances" bug).

**Evolução tab** (v4.80). `EvolucaoSim` re-runs the Monte Carlo at every point of a time axis
"as if" only the results known up to that point existed, and plots one team's metric. For
A/B/C the axis is rounds 0..maxR and the mechanism is just `mergedRes[sk].filter(r => r.r <= N)`
— `simMC_single` decides played-vs-simulated purely from the `res` array, so no engine change
is involved. For Série D and Copa do Brasil the axis is knockout phases, driven by an optional
trailing `opts` argument on the engine entry points: `simMC`/`simMC_async` take
`{ignoreUser}` (clears `BC_USER`), `simMC_D`/`simMC_D_async` take `{koMask}` (a Set of phase
letters B..G whose real results may be used; `s180` receives the phase letter at each call
site), `simMC_CB` takes `{cbMask}` (a Set of `'R32'`/`'R16'`). `null`/absent = the old
behaviour. `SD_KO_CODES` is deliberately *not* masked (it is bracket structure, not a result).
One sweep stores scalar metrics for every team, so switching team/metric never recomputes;
the cache and progress live in `SimuladorUnificado` (tabs unmount on switch) and a sweep is
mutually exclusive with "Simular Tudo" because the `BC_USER` reset is global. Known uniform
leaks: `applyCBToLeague` feeds Copa do Brasil legs into the initial Elo at every point, and
the Copa sweep uses the current dashboard's evolved strengths at every point.

**Ranking Nacional de Clubes** (v4.66–v4.70). `RNC_2026` holds the CBF's published 2026 table
(235 clubs) plus `s5` = Σ(P2021..P2025), which the CBF does *not* publish — it is reconstructed
from the league and Copa do Brasil classifications of those years by `scripts/rnc_data/` (see
its README). The check that matters: `5·P25+4·P24+3·P23+2·P22+1·P21` reproduces the published
value for all 235 clubs with no divergence, which validates the points scale, the parsing and
the name reconciliation at once. `buildRNC` projects 2027 (`RNC2026 + 5·P26 − s5`) with P26 from
the Monte Carlo. The **`rnc` tab** renders it.

**Série D 2027** (v4.68–v4.70). `EST_FILA_2027` is the per-state succession queue. Two rules for
a vacated state slot, with *opposite* destinations — swapping them yields a plausible, wrong
table: a club that **is promoted to Série C** frees its slot to the next in the *same state*;
a club with a **double slot** (state + Critério 3) sends the surplus to the *Ranking Nacional*
and the state gains nothing. `build2027Alloc` applies the four criteria of Art. 2º of the REC
per draw, coupling the C and D simulations through the traces. `sorteio2027` projects the 16
groups as a min-cost flow where the max-3-per-state cap is the **arc capacity**, so an invalid
group is unrepresentable rather than repaired. All of it lives in the Série D `cl27` sub-tab.

**Per-series data** is hardcoded as `S{A,B,C}_TAB` (fixtures), `_RES` (real results played), `_RANKING`, `_DATES`, `_NM`, plus `_META` objects (e.g. `nReb` relegation count, zone cutoffs — these encode 2026 CBF format changes like Série C having only 2 relegated). Copa do Brasil uses `CB_RES_IDA`/`CB_RES_VOLTA` for the round of 32 and `CB_R16_PAIRS` for the (drawn) round of 16. Since v4.84 the bracket from the quarterfinals to the final is also real: `applyCbAuto` turns the `QF`/`SF`/`F` rows of `results.json.cb` into `CB_AUTO.ko` (ties in the same `{a, b, sc: {g1a, g1b, g2a, g2b}, pen}` convention as the round of 16, `a` = first-leg host) plus `CB_AUTO.sfLinks` (which quarterfinal feeds each semifinal, resolved by name once the PDF lists the semifinalists). `cbKoPlan(r16winners, cbMask)` is the single place both `simMC_CB` and the tab's `runBracket` ask for that structure: the real quarterfinal pairings are used only when the eight simulated round-of-16 winners are exactly the real eight (otherwise the old per-simulation draw), semifinals follow `sfLinks`, real scores enter per phase mask, and — like `SD_KO_CODES` — the pairings themselves are never masked. The 2026 edition draws the whole bracket at the quarterfinal stage (GR 119 Inter×Grêmio, 120 Cruzeiro×Atlético-MG, 121 Vasco×Vitória, 122 Palmeiras×Santos; semis 123/124; final GR 125 on 06/12), so "sorteio a cada fase" no longer describes it. The Evolução Copa axis gained "Após quartas"/"Após semis"/"Após a final" points (masks `QF`/`SF`). Results are merged with user-fetched results from `localStorage`.

**`UpdaterPanel`** ingests new real results: it downloads a CBF PDF through the `allorigins.win` CORS proxy, then calls the Anthropic Messages API (`api.anthropic.com/v1/messages`, model `claude-sonnet-4-6`) with the PDF as a document block to extract finished matches as a JSON array, which is merged and persisted. API key resolution order: `window.__ANTHROPIC_API_KEY__` (build-time placeholder `__ANTHROPIC_API_KEY__`, optionally replaced by a CI secret) → `localStorage['simUni_apiKey']` → manual entry. There is a fully manual fallback ("Copiar prompt" + paste JSON) when no key/proxy is available.

**localStorage keys**: `simUni_apiKey`, `simUni_fetchedRes`.

**Automatic result updates** (added separately from the app source): a twice-weekly GitHub Action (`.github/workflows/update-tables.yml`, crons `0 14 * * 1` and `0 9 * * 5` — Monday 14:00 UTC / 11:00 BRT and Friday 09:00 UTC / 06:00 BRT — plus manual dispatch) on the repo `agamemnon140/brasileiro-2026` runs `scripts/fetch_tables.mjs`: it discovers the current official CBF "Tabela Detalhada" PDFs via the public Strapi CMS (`cms.cbf.com.br/api/championship-documents`, type "Complemento de Tabela" — the blob URL hash changes weekly; since v4.84 only a document titled "Tabela Detalhada" is accepted: in September 2026 the CBF removed the Séries C and D detailed tables from the CMS and left only the "Tabela Básica", a fixture list with no scores, which the old `/tabela/i` filter happily picked — 0 results extracted and the PDF cache pointing at a score-less PDF. Now the run warns and skips that série with the cache untouched. Since 27/09 the **Série C second phase no longer depends on the PDF**: `fetchQuadCGweb` reads the CBF site's own match API ("GWEB", `https://www.cbf.com.br/api/cbf/jogos/campeonato/<edition>/rodada/<n>/fase`, editions in `GWEB_EDITION`: A 1260611, B 1260612, C 1260613, D 1260635, Copa 1260615, taken from `/api/cbf/campeonatos/anos`), which returns every phase's games for round n with score (`gols` null when unplayed), date and per-side penalties, and feeds the same `mergeQuadRows` merge before the PDF loop on every run at no API cost. `QUAD_GWEB_DRY=1 node scripts/fetch_tables.mjs` (with `NODE_EXTRA_CA_CERTS=scripts/cbf-ca.pem`; the site shares the CMS's incomplete Sectigo chain) prints what it would ingest. The same API also feeds the **league phase of A/B/C** (`fetchLigaGweb`, first phase only for C — group "GRUPO A"; per-série name maps in `GWEB_NORM_S`, since "Botafogo" is Botafogo-RJ in A and Botafogo-SP in B), and unlike every other source it is **authoritative**: it runs before the PDF loop and, when a recorded score differs, it overwrites it with a `::warning::Corrigido pela API da CBF` line and a `corrigido_de` field on the row (`last_run.corrigidos` counts them). That exists because the PDF-plus-model extraction once stored Fortaleza 1×0 Operário-PR (R25 of B; official 1×1) and the never-overwrite rule would have kept it forever. Games that started less than 3 h ago are skipped (a live match shows a partial score). `LIGA_GWEB_DRY=1` prints, per série, new games and scores that would be corrected. Only the D knockout and the Copa do Brasil still depend on the PDFs), downloads them (cms.cbf.com.br serves an incomplete TLS chain, hence `NODE_EXTRA_CA_CERTS` pointing at the vendored `scripts/cbf-ca.pem`), extracts played league-phase results with the Anthropic API (PDF document block) and merges them into `results.json` at the repo root, committing on change so GitHub Pages redeploys. Since v4.59 it also covers the **Série D knockout**: the D PDF's mata-mata legs (GR code + ida/volta + penalties) go into the `ko_d` field of `results.json`, which the app converts into `SD_KO_AUTO`/`SD_KO_PART_AUTO` overlays (precedence: user edits > hardcoded > automation) feeding the MC, the bracket defaults, the Geral tab and the Config log. Since v4.64 the Copa do Brasil round of 16 goes into `cb` (`applyCbAuto` → `CB_AUTO`, user edits win); since v4.84 the same pass extracts everything from the round of 16 onward as one row per leg (`fase` R16/QF/SF/F, `gr` = CBF tie number, `leg` ida/volta, `data`, `pen_c`/`pen_f`, `gc`/`gf` null for an unplayed game — that is how the app learns the bracket before a phase is played; round-of-16 rows still require a score and a real `CB_R16_PAIRS` pairing), keyed by `fase|casa|fora`, never overwriting a recorded score, and `cb_added` now counts in `total_new`. The final is a single game in the app's model, matching the one row (GR 125, 06/12) in the CBF table. Since v4.81 the **Série C second phase** goes into `quad_c`: the C PDF gets a third extraction pass that returns the whole quadrangular fixture (CBF groups B/C, rounds 1–6, plus the final once its teams are known) with `gc`/`gf` null for unplayed games, so the app knows the real group composition before round 1; `applyQuadCAuto` turns it into `QUAD_C_AUTO` (groups in CBF-letter order → app groups A/B, per-game scores, final legs with penalties). The C MC uses the real groups only when the simulated top-8 equals the real one (`quadCRealGroups`), so the Evolução per-round truncation keeps the presumed 1-4-5-8 / 2-3-6-7 split; real scores take precedence over user edits (unlike `ko_d`), and `LeaguePhaseEdit` locks played games. When the C PDF URL is cached but `quad_c` is still empty, the run downloads the PDF and does only that pass. `last_run.quad_added` is part of `total_new`; the Config log lists those games as série C with round `Q<grupo><rodada>` or `F·i`/`F·v`. It skips games already hardcoded in the app by parsing `SA/SB/SC_RES` (and `SD_F2_REAL`/`SD_F3_REAL` for D — keep those parses updated when consolidating new knockout phases) out of `index.html`. The app loads `results.json` on mount via a `useEffect` (injected just after `handleSearchResults` in `SimuladorUnificado`, in both `index.html` and `brasileirao-2026.html`), feeds it through the same `handleSearchResults` pipeline, and the dashboard auto-run waits for that fetch to settle (v4.55c). Server-side guardrails: canonical-team allowlist + `NORM_NAME` map (kept in sync by hand with the app team lists), score range 0–14, round 1–38, never overwrites a recorded score (logs conflicts), per-run volume cap. An earlier web-search-based Action (`fetch_results.mjs` + `update-results.yml`, Anthropic `web_search` tool) was retired in favor of the official PDFs — see git history if it's ever needed again. The Action needs the repo secret `ANTHROPIC_API_KEY`; the API key is never exposed client-side here.

**Reading the automation's output correctly.** The envelope carries a `last_run` block (`{at, added, ko_added, total_new}`) recording what **that run** contributed. The badge under the app title shows that delta — `📡 Tabelas CBF atualizadas em <data> · +N novo(s) nesta atualização` — and keeps the cumulative total in its `title` tooltip; the Config tab still lists the cumulative figure, labelled "acumulados". Envelopes written before `last_run` existed fall back to the old cumulative wording, so both shapes render.

Because the writer returns early when nothing changed, `results.json` is only rewritten on a real change: `updated_at`/`last_run` always describe the last **effective** update, and a no-op run leaves the badge showing the previous one. That is intended — but it means the badge alone cannot tell you whether this week's run executed. Check the Action for that. A run legitimately adds nothing when the CBF has not republished that série's PDF (the discovered blob URL is unchanged from the previous week), so "no new results" is an expected mid-week outcome and is not evidence of a broken key or exhausted credits. Real API failures surface as a failed step in the Action, not as a silent empty diff; `gh run view <id> --log` and its `Resumo: +X liga + Y mata-mata D novos, ...` line are the ground truth for any given run.

## Prediction evaluation (`eval/`)

`eval/` measures how well the model actually predicts — short term (per-match V/E/D,
walk-forward) and long term (projected table via Monte Carlo). Run it with
`node eval/run.cjs`; see `eval/README.md` for the design and `eval/REPORT.md` for the
current findings.

**`eval/` only ever READS the app.** It slices the engine out of `index.html` in memory
(via the pre-existing `scripts/engine.cjs`) and writes only to `eval/out/` and
`eval/REPORT.md`. It never edits the app and never runs `build_html.js`. `run.cjs` aborts
if the checkout is behind `origin/main` or if `index.html`/`results.json` are dirty —
evaluating a stale copy measures a model that is not live, which this file already warns
about above.

Two findings from `eval/` change how the config should be read, so they belong here:

- **`kElo` and `homeAdv` do not affect predictions** in the mode the app runs (`eo=false`,
  ATK/DEF — `dashEo` defaults to `false` and the UI labels it "default"). `calcL` computes λ
  purely from `atk`/`def`; `updR` evolves Elo and atk/def on separate tracks and the running
  Elo never feeds back into λ. Measured, not inferred: Brier delta is *exactly* zero for
  `kElo` 16→64 and `homeAdv` 100→400, in all four series. The only channel for prior
  strength is the **initial** Elo, through `initLeague → initAD`. Do not "tune" those two
  parameters expecting predictive change — and note `backtestSeries` is called without the
  `eo` argument, so the app's own calibration tab always measures ATK/DEF regardless of what
  the dashboard is running.
- **`targetRatio` is only live for Série A.** `initLeague` computes
  `rawSpread = log(targetRatio)/log(maxElo/minElo)` and caps it at `maxSpread` (5). Séries B,
  C and D have narrow initial-Elo ranges, so `rawSpread` is 8.9–47 and the cap binds — their
  Brier is bit-identical across `targetRatio` 1.5→8.0. Only Série A (rawSpread 4.54) sits
  below the cap and responds. The parameter looks global and is not.
- **What the seed transmits is mostly SPREAD, not ordering.** Rescaling every seed to a
  common range and then shrinking it by a factor `k` produces a U-shaped Brier curve in every
  série, and at the optimum the orderings ("by hand", RNC, previous year) converge to nearly
  the same value. Série A currently runs at k≈1.06 against a measured optimum of 0.35–0.50 —
  it is the one série whose seed spread is wrong, and also the one with the significant home
  bias. B (k≈0.17) and C (k≈0.09) are already near their optima. Full tables in
  `eval/REPORT.md` §3.
- **The home-advantage bias tracks `lambdas[serie].pesoCasa`.** Séries A (0.652) and D
  (0.604) over-predict home wins by 9.1 and 5.6 pp respectively, both statistically
  significant; B and C (0.583) are within noise. Before changing `pesoCasa`, check the
  observed split in `eval/out/curto.json`.

When `simMC` is called from a harness, pass the **parsed** fixture (`parseTab(SX_TAB, SX_NM,
SX_DATES)`), not the raw `SX_TAB` strings — the raw form silently produces nonsense (100%
title, 0 points) instead of failing.

## Conventions

- The big comment block at the top of `index.html` is a **running changelog** (v4.x). When making a substantive change, add a dated/versioned entry there describing the fix and its rationale — this is the project's primary record of why things are the way they are.
- Series-format rules (relegation counts, access slots, playoff/quadrangular structures) reflect specific **2026 CBF regulations** and have been corrected repeatedly; verify against the regulation before changing zone cutoffs or `nReb`.
- Watch for call-stack overflow: the code uses a `minMax()` loop instead of `Math.min/max(...arr)` because Série D produces very large sample arrays (~960k).
